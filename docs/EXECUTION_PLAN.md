# Be Fast — خطة التنفيذ

نفّذ المراحل بالترتيب، مرحلة واحدة في كل مرة. لا تبدأ مرحلة قبل أن تتحقق كل «معايير القبول» للتي قبلها.
السلوك المطلوب معرَّف في `docs/SPEC.md`؛ هذا الملف يحدد **ماذا تبني ومتى وكيف تثبت أنه يعمل**.

---

## أ. البنية التقنية المعتمدة

مستودع واحد (monorepo) بـ pnpm workspaces + Turborepo، TypeScript بوضع `strict` في كل شيء.

```
be-fast/
├─ apps/
│  ├─ api/          Fastify + Zod + Prisma + PostgreSQL + pg-boss
│  ├─ admin/        Next.js (App Router) + Tailwind، RTL
│  ├─ customer/     Expo (React Native) + expo-router
│  └─ restaurant/   Expo (React Native) + expo-router
├─ packages/
│  ├─ domain/       منطق نقي بلا I/O: المال، آلة الحالات، ساعات العمل، الإتاحة، الهاتف
│  ├─ contracts/    مخططات Zod للطلبات والاستجابات + الـ enums + أكواد الأخطاء
│  ├─ i18n/         النصوص العربية ودوال تنسيق التاريخ
│  ├─ ui-tokens/    الألوان والمسافات والخطوط
│  └─ api-client/   عميل HTTP مطبوع الأنواع مبني على contracts، تستعمله التطبيقات الثلاثة
├─ docs/
├─ docker-compose.yml   PostgreSQL + MinIO للتطوير والاختبار
└─ AGENTS.md
```

| الجانب | القرار | السبب |
|---|---|---|
| قاعدة البيانات | PostgreSQL عبر `DATABASE_URL` | لا ارتباط بمزوّد بعينه |
| ORM والترحيلات | Prisma، ترحيلات ملتزَمة في المستودع | — |
| المهام المجدولة | pg-boss | يعمل على PostgreSQL نفسه، لا حاجة لـ Redis |
| الصور | تخزين متوافق مع S3 (MinIO محلياً)، معالجة بـ sharp | — |
| التحديث اللحظي | سحب دوري (polling) | أبسط وأوثق على الشبكات الضعيفة؛ لا WebSocket في MVP |
| حالة التطبيق | TanStack Query مع تخزين دائم + Zustand، AsyncStorage | حفظ السلة والبيانات المخبأة |
| الخرائط | لا مكتبة خرائط | الإحداثيات اختيارية من GPS فقط |
| الاختبارات | Vitest؛ اختبارات الخادم على PostgreSQL حقيقي من docker-compose | لا mocks للقاعدة |
| المزوّدات الخارجية | واجهات `OtpProvider`, `PushProvider`, `StorageProvider` مع تنفيذ تطوير | لم يُتحقق من أي مزوّد داخل سوريا بعد |

**الإصدارات:** لا تكتب أرقام إصدارات من الذاكرة. ثبّت أحدث إصدار مستقر متوافق وقت التنفيذ، ثبّته بدقة (بلا `^`)، وسجّل الإصدارات في `docs/VERSIONS.md`. عند الشك في واجهة مكتبة، اقرأ توثيقها الحالي.

**اتجاه الاعتماد:** `domain` لا يعتمد على شيء. `contracts` يعتمد على `domain`. التطبيقات تعتمد على الحزم. لا حزمة تعتمد على تطبيق. لا تطبيق يستورد من تطبيق آخر. لوحة الإدارة لا تتصل بالقاعدة مباشرة؛ كل شيء عبر الـ API.

**مسارات الـ API:** ثلاث بادئات بمصادقة منفصلة: `/customer/*`، `/restaurant/*`، `/admin/*`، إضافة إلى `/public/*` (تصفح بلا حساب) و`/auth/*`.

## ب. الأوامر المعيارية

يجب أن تعمل هذه من جذر المستودع بعد المرحلة 0، وتبقى خضراء بعد كل مرحلة:

```
pnpm install
pnpm db:up          # تشغيل docker-compose
pnpm db:migrate     # تطبيق الترحيلات
pnpm db:seed        # بيانات تجريبية
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

### المرحلة 1 — حزمة `domain` (منطق نقي)
لا I/O، لا تاريخ من `Date.now()` داخل الدوال (الوقت يُمرَّر كمعامل).

**المهام**
1. `money`: نوع `Minor`، `calcItemTotal`، `calcOrderTotals`، `calcCommission`، `formatMoney(amountMinor, displayMode)`.
2. `phone`: `normalizeSyrianPhone` و`maskPhone`.
3. `order-state`: الحالات، `TERMINAL_STATES`، `canTransition(from, to, actor, orderType)`، `allowedTransitions(...)`، أكواد الأسباب.
4. `hours`: `isOpenAt(periods, instantUtc)` بتوقيت `Asia/Damascus` مع فترات تعبر منتصف الليل.
5. `availability`: `isOrderable(...)` تجمع شروط SPEC §6.
6. `menu-validation`: التحقق من اختيارات الخيارات مقابل `minSelect/maxSelect`.

**القبول**
- اختبارات وحدة تغطي على الأقل:
  - مثال SPEC §3 (`80000 + 10000 → 90000`، العمولة `8000`).
  - التقريب: `foodSubtotalMinor = 33333`، `bps = 1000` → `3333`.
  - كل صف في جدول الانتقالات مسموح، وكل زوج (حالة، حالة) غير مذكور مرفوض — يُولَّد آلياً من الجدول، لا يُكتب يدوياً.
  - لا انتقال يخرج من أي حالة نهائية، لأي فاعل.
  - `KITCHEN` لا يقبل ولا يرفض ولا يسلّم.
  - `READY → DELIVERED` مسموح للاستلام ومرفوض للتوصيل؛ `READY → OUT_FOR_DELIVERY` العكس.
  - ساعات العمل: 18:00–02:00 مفتوح عند 01:30 ومغلق عند 02:00؛ يوم بلا فترات مغلق.
  - الهاتف: الصيغ الأربع المقبولة تعطي `+9639XXXXXXXX`؛ رقم أرضي ورقم ناقص يُرفضان.
  - `formatMoney(80000,'OLD')` → `80,000 ل.س`؛ `formatMoney(80000,'NEW')` → `800 ل.س`؛ `formatMoney(80050,'NEW')` → `800.50 ل.س`.
- تغطية الحزمة ≥ 95% للأسطر.

### المرحلة 2 — مخطط القاعدة والبيانات الأولية
**المهام**
1. مخطط Prisma للجداول:
   `Governorate`, `City`, `Neighborhood`, `FoodCategory`,
   `Customer`, `CustomerAddress`, `OtpChallenge`, `RefreshToken`,
   `Restaurant`, `RestaurantCategory`, `RestaurantDocument`, `Branch`, `OpeningPeriod`, `DeliveryZone`, `RestaurantUser`,
   `MenuSection`, `MenuItem`, `ItemSize`, `OptionGroup`, `Option`, `PriceChangeLog`,
   `Order`, `OrderItem`, `OrderItemOption`, `OrderStatusEvent`,
   `LedgerEntry`, `Complaint`,
   `AdminUser`, `AuditLog`, `PlatformSetting`.
2. قيود على مستوى القاعدة (لا تكتفِ بالتحقق في الكود):
   - فريد: `Customer.phone`، `RestaurantUser.phone`، `AdminUser.email`، `Order.orderNumber`، `(Order.customerId, Order.idempotencyKey)`، `(DeliveryZone.branchId, neighborhoodId)`.
   - فريد جزئي: `LedgerEntry(orderId) WHERE type = 'COMMISSION_ACCRUED'`.
   - `CHECK`: كل حقل `*Minor` للأسعار `>= 0`، `quantity BETWEEN 1 AND 50`، `commissionRateBps BETWEEN 0 AND 10000`، `minSelect <= maxSelect`.
   - مفاتيح أجنبية بـ `ON DELETE RESTRICT` للطلبات والقيود المالية.
   - trigger يمنع `UPDATE`/`DELETE` على `OrderStatusEvent` و`LedgerEntry` و`AuditLog`.
3. فهارس: `Order(branchId, status, createdAt)`، `Order(customerId, createdAt)`، `Order(status, createdAt)`، `DeliveryZone(neighborhoodId)`، `LedgerEntry(restaurantId, createdAt)`.
4. `db:seed`: محافظة ومدينة و8 أحياء، 7 تصنيفات (شاورما، بيتزا، بروستد، مشاوي، برغر، حلويات، مشروبات)، 3 مطاعم معتمدة بمنيو كامل (أحجام وخيارات إلزامية واختيارية)، مطعم `PENDING_REVIEW`، عميل، حساب `SUPER_ADMIN`، إعدادات المنصة الابتدائية. أسماء المناطق في seed وهمية وواضح أنها تجريبية.

**القبول**
- `db:migrate` ثم `db:seed` ينجحان على قاعدة فارغة، و`db:seed` آمن عند إعادة التشغيل.
- اختبارات تثبت أن القاعدة ترفض: قيد عمولة ثانٍ لنفس الطلب، تعديل صف في `LedgerEntry`، حذف صف من `OrderStatusEvent`، مفتاح تكرار مكرر لنفس العميل، سعر سالب.

### المرحلة 3 — المصادقة والصلاحيات
**المهام**
1. `/auth/customer/otp/request`، `/auth/customer/otp/verify`، `/auth/refresh`، `/auth/logout`.
2. `/auth/restaurant/register` (مالك: هاتف + OTP + كلمة مرور)، `/auth/restaurant/login`.
3. `/auth/admin/login` (بريد + كلمة مرور + TOTP)، سكربت `pnpm admin:create`.
4. وسيط مصادقة لكل بادئة يفحص `aud`، ووسيط أدوار للمطعم والإدارة.
5. تحديد المعدل حسب SPEC §5 و§16. `DevOtpProvider` يطبع الرمز في السجل.
6. صيغة الأخطاء الموحدة ومعالج أخطاء مركزي.

**القبول** (اختبارات تكامل)
- رمز عميل على مسار `/restaurant/*` أو `/admin/*` → 401/403، والعكس لكل تركيبة.
- رمز OTP خاطئ 5 مرات يُبطل التحدي؛ رمز منتهٍ يُرفض؛ الرمز لا يُستعمل مرتين.
- الطلب السادس لـ OTP لنفس الهاتف خلال ساعة → 429.
- refresh token مستعمل سابقاً يُرفض ويُبطل السلسلة.
- لا يظهر في السجلات هاتف كامل ولا رمز دخول.

### المرحلة 4 — المناطق والتصنيفات وتسجيل المطعم
**المهام**
1. إدارة: CRUD للمحافظات/المدن/الأحياء والتصنيفات (تعطيل بدل الحذف عند الاستعمال).
2. عام: `GET /public/geo` (شجرة المناطق الفعالة)، `GET /public/categories`.
3. مطعم: إنشاء/تعديل ملف المطعم، رفع الشعار والغلاف والمستندات، ساعات العمل، مناطق التوصيل، `minOrderMinor`، `pickupEnabled`، إرسال للمراجعة.
4. إدارة: قائمة المطاعم حسب الحالة، موافقة/رفض/تعليق/إعادة تفعيل مع سبب، تعديل `commissionRateBps`.
5. `StorageProvider` + معالجة الصور (320/640 WebP) + روابط موقّعة للمستندات.
6. `AuditLog` لكل عملية إدارية هنا.

**القبول**
- مطعم `DRAFT`/`PENDING_REVIEW`/`REJECTED`/`SUSPENDED` لا يظهر في أي مسار `/public/*` أو `/customer/*`.
- لا يمكن الإرسال للمراجعة قبل اكتمال: الاسم، تصنيف، حي، فترة عمل، منطقة توصيل، مستند.
- مستخدم مطعم (أ) → 404 على موارد مطعم (ب) (ملف، مناطق، مستندات).
- رابط مستند لا يعمل بلا توقيع، وينتهي بعد 5 دقائق.
- تغيير العمولة يكتب `AuditLog` فيه القيمة قبل وبعد.
- رفع ملف ليس صورة، أو أكبر من 5MB → 4xx.

**المهام**
1. مطعم: CRUD للأقسام والأصناف والأحجام ومجموعات الخيارات والخيارات، ترتيب، حذف ناعم.

- النسخ ينتج صنفاً مستقلاً بكل فروعه و`isAvailable = false`.
- تغيير سعر حجم ينتج صف `PriceChangeLog` واحداً صحيحاً.

### المرحلة 6 — تصفح العميل
**المهام**
1. `GET /public/restaurants?neighborhoodId=&categoryId=&q=&cursor=` — يعيد لكل مطعم: الاسم، الشعار، التصنيفات، `isOrderable`، سبب عدم الإتاحة، `deliveryFeeMinor`، `minOrderMinor`، `etaMinutes`. الترتيب: المتاح أولاً.
2. `GET /public/restaurants/:id?neighborhoodId=` — الملف والمنيو الكامل مع توفر كل صنف الآن.
3. البحث `q` في اسم المطعم واسم الصنف، مع تطبيع عربي (توحيد أ/إ/آ→ا، ة→ه، ى→ي، إزالة التشكيل والتطويل) على الطرفين.
4. `/customer/addresses` CRUD + الافتراضي. `/customer/me`.
5. ترقيم بالمؤشر (cursor)، 20 عنصراً للصفحة.

**القبول**
- مطعم لا يخدم الحي لا يظهر. مطعم مغلق يظهر بـ `isOrderable = false` وسبب `CLOSED`.
- مطعم `acceptingOrders = false` → `PAUSED`. فرع غير متصل منذ >120ث → `OFFLINE`.
- البحث عن «شاورما» يجد «شاورمة» والعكس؛ «احمد» يجد «أحمد».
- عميل (أ) لا يقرأ ولا يعدّل عنوان عميل (ب).
- استجابة قائمة 20 مطعماً بلا استعلامات N+1 (اختبار يعدّ الاستعلامات).

### المرحلة 7 — الطلبات (القلب)
**المهام**
1. `POST /customer/orders` كما في SPEC §8.1 حرفياً.
2. `GET /customer/orders`، `GET /customer/orders/:id` (مع سجل الحالات)، `POST /customer/orders/:id/cancel`.
3. `GET /restaurant/orders/active`، `GET /restaurant/orders?status=&from=&to=`، `GET /restaurant/orders/:id`.
4. `POST /restaurant/orders/:id/transition { to, prepMinutes?, reasonCode?, note? }` — مسار واحد يستعمل `canTransition`.
5. `POST /admin/orders/:id/cancel`، قائمة «تحتاج معالجة».
6. مهمة pg-boss كل 15 ثانية: التذكير، وسم `needsAttention`، و`PENDING → EXPIRED`.
7. تحديث `Branch.lastSeenAt` من `GET /restaurant/orders/active`.
8. `PushProvider` (تنفيذ تطوير يسجّل فقط) يُستدعى عند: طلب جديد للمطعم، وكل تغيير حالة للعميل. فشله لا يُفشل العملية.
9. حجب بيانات العميل للمطعم بعد 24 ساعة ولدور `KITCHEN` دائماً.
10. `/customer/orders/:id/complaint` والشكاوى في الإدارة.

**القبول** (اختبارات تكامل على قاعدة حقيقية)
- **التكرار:** 10 طلبات متزامنة بنفس `Idempotency-Key` → طلب واحد في القاعدة، وكل الاستجابات تحمل نفس المعرّف.
- **السباق:** قبول ورفض متزامنان لنفس الطلب → واحد ينجح والآخر 409، وصف `OrderStatusEvent` واحد.
- **السباق مع الانتهاء:** قبول يتزامن مع مهمة الانتهاء → نتيجة واحدة متسقة.
- **السعر:** العميل يرسل أسعاراً مزوّرة في الجسم → تُتجاهل. تغيّر السعر بين السلة والتأكيد → 409 `PRICE_CHANGED` ولا طلب.
- **اللقطة:** بعد إنشاء الطلب، تغيير اسم الصنف وسعره وحذفه لا يغيّر شيئاً في `GET` للطلب.
- كل كود خطأ في SPEC §8.1 له اختبار.
- كل انتقال غير مسموح → 409 `INVALID_TRANSITION` (يُولَّد من جدول `domain`).
- طلب مرفوض لا يصل `DELIVERED` بأي مسار ولأي فاعل، بمن فيهم الإدارة.
- إعادة إرسال انتقال منفَّذ → 200 بلا صف جديد.
- الطلب لا يُقبل تلقائياً: بعد `expireAfterSec` يصير `EXPIRED`.
- `KITCHEN` لا يرى هاتفاً ولا عنواناً ولا مبالغ في أي استجابة.
- مطعم (أ) → 404 على طلب مطعم (ب). عميل (أ) → 404 على طلب عميل (ب).
- فشل `PushProvider` (يرمي استثناء) لا يمنع إنشاء الطلب.

### المرحلة 8 — المالية والتقارير
**المهام**
1. قيد `COMMISSION_ACCRUED` داخل معاملة انتقال `DELIVERED`.
2. إدارة: `GET /admin/finance/restaurants` (الأرصدة)، كشف قيود مطعم، `POST …/payments`، `POST …/adjustments`.
3. مطعم (OWNER): `GET /restaurant/reports/summary?period=day|week|month&date=` بالأرقام الأربعة في SPEC §11، و`GET /restaurant/finance/ledger`.
4. إدارة: مؤشرات أساسية (نسبة الإكمال، نسبة القبول، متوسط زمن الرد، نسب الإلغاء حسب السبب).

**القبول**
- طلب `DELIVERED` → قيد واحد بقيمة `commissionMinor`. انتقالان متزامنان إلى `DELIVERED` → قيد واحد.
- `REJECTED`/`EXPIRED`/`CANCELLED`/`DELIVERY_FAILED` → لا قيد.
- تغيير نسبة المطعم بعد إنشاء الطلب لا يغيّر عمولة ذلك الطلب.
- الرصيد = مجموع القيود في سيناريو: 3 طلبات مكتملة + دفعة + تسوية سالبة.
- الأرقام الأربعة تختلف وتطابق قيماً محسوبة يدوياً في اختبار يضم طلبات مكتملة وملغاة وأخرى برسوم توصيل.
- حدود اليوم بتوقيت دمشق: طلب 23:30 UTC يُحسب في اليوم التالي محلياً.
- تسوية بلا سبب تُرفض. `FINANCE` و`SUPER_ADMIN` فقط يكتبون قيوداً. كل قيد يكتب `AuditLog`.

### المرحلة 9 — لوحة الإدارة (ويب)
**المهام**
1. تخطيط RTL، تسجيل دخول مع TOTP، حماية المسارات حسب الدور، قائمة جانبية بأقسام SPEC §12.
2. تنفيذ كل قسم في جدول SPEC §12 فوق الـ API الموجود. لا منطق أعمال في الواجهة.
3. الرئيسية تتحدث كل 15 ثانية.
4. كل إجراء حساس يطلب تأكيداً ويعرض السبب الإلزامي.
5. متجاوبة حتى عرض 360px.

**القبول**
- اختبارات Playwright للمسارات: دخول → موافقة على مطعم معلّق → يظهر في `/public/restaurants`؛ تسجيل دفعة → الرصيد يتغير؛ إلغاء طلب → يظهر في سجل التدقيق.
- `SUPPORT` لا يرى أزرار المالية، وطلبها مباشرة من الـ API يعيد 403.
- `dir="rtl"` و`lang="ar"` على الجذر؛ لا نص إنجليزي ظاهر للمستخدم.
- فحص axe بلا مخالفات تباين.

### المرحلة 10 — تطبيق المطعم (Android)
**الشاشات**
1. دخول، تسجيل مالك، معالج تسجيل المطعم (خطوات SPEC §6) مع حالة المراجعة.
2. **الطلبات** (الشاشة الرئيسية): تبويبات جديدة / قيد التحضير / جاهزة / خرجت للتوصيل / مكتملة اليوم. الطلب الجديد أعلى القائمة.
3. تفاصيل الطلب: الأصناف والكميات والخيارات والملاحظات بخط كبير، بيانات العميل، زر اتصال، أزرار الانتقال المسموحة فقط (من `allowedTransitions`).
4. قبول: اختيار وقت التحضير بأزرار سريعة (10/15/20/30/45/60). رفض/إلغاء/تعذر تسليم: اختيار سبب.
5. المنيو: أقسام وأصناف، مفتاح توفر سريع لكل صنف، تحرير كامل، نسخ.
6. مفتاح «إيقاف استقبال الطلبات» ظاهر دائماً في شاشة الطلبات.
7. الإعدادات: ساعات العمل، مناطق التوصيل، الموظفون (OWNER). التقارير (OWNER).

**السلوك** حسب SPEC §9: سحب كل 10ث، تنبيه صوتي متكرر، إبقاء الشاشة مضاءة، شريط انقطاع الاتصال، عدّ تنازلي للمهلة.

**القبول**
- اختبارات مكوّنات لشاشة الطلبات: الأزرار الظاهرة لكل (حالة × دور × نوع طلب) تطابق `allowedTransitions`.
- واجهة `KITCHEN` لا تعرض هاتفاً ولا مبالغ ولا أزرار قبول/رفض.
- عند فشل السحب يظهر شريط الانقطاع، ويختفي عند أول نجاح.
- ضغطتان سريعتان على «قبول» ترسلان طلباً واحداً.
- `pnpm --filter restaurant build:android` ينتج APK. وثّق خطوات التشغيل اليدوي على جهاز/محاكي في `docs/RUNBOOK.md`.

### المرحلة 11 — تطبيق العميل (Android)
**الشاشات**
1. اختيار المنطقة عند أول تشغيل (محافظة → مدينة → حي)، بلا حساب.
2. الرئيسية: العنوان المختار، بحث، تصنيفات، مطاعم الحي (المتاحة أولاً، مع الرسوم والحد الأدنى والوقت).
3. المطعم: معلومات، أقسام المنيو، الأصناف غير المتوفرة باهتة.
4. الصنف: حجم، مجموعات خيارات مع فرض الإلزامي، ملاحظة، كمية، سعر محدَّث.
5. السلة: مطعم واحد. إضافة صنف من مطعم آخر تعرض: «سلتك فيها طلب من مطعم تاني. بدك تفضّيها وتبدأ من جديد؟».
6. إتمام الطلب: نوع (توصيل/استلام)، العنوان، تفصيل المبالغ، ملاحظة، «الدفع نقداً عند الاستلام»، OTP عند الحاجة، تأكيد.
7. متابعة الطلب: خط الحالات، الوقت التقديري، إلغاء (في `PENDING` فقط)، اتصال بالمطعم، شكوى.
8. طلباتي، عناويني، حسابي (حذف الحساب).

**السلوك** حسب SPEC §10 حرفياً، خصوصاً تدفق تأكيد الطلب ومفتاح التكرار.

**القبول**
- اختبارات مكوّنات:
  - زر «أضف للسلة» معطّل حتى تُستوفى المجموعات الإلزامية.
  - السعر المعروض يطابق `calcItemTotal` من `domain` لكل تركيبة.
  - انقطاع الشبكة عند التأكيد: لا شاشة نجاح؛ إعادة الإرسال بنفس المفتاح؛ ثم رسالة «ما قدرنا نتأكد…».
  - استجابة `PRICE_CHANGED` تعرض الإجمالي الجديد وتطلب تأكيداً.
  - إعادة تشغيل التطبيق تُبقي السلة والعنوان.
  - بلا اتصال: آخر قائمة مطاعم محفوظة تظهر مع وسم التقادم.
- لا نص عربي حرفي خارج `packages/i18n` (قاعدة lint).
- لا لون حرفي خارج `packages/ui-tokens` (قاعدة lint).
- `pnpm --filter customer build:android` ينتج APK.

### المرحلة 12 — التحقق الشامل والتسليم
**المهام**
1. اختبار نهاية-لنهاية على الـ API يمثل رحلة كاملة: تسجيل مطعم → موافقة → منيو → طلب عميل → قبول → تحضير → جاهز → خرج → تسليم → قيد العمولة → دفعة → رصيد صفر. ورحلات: رفض، انتهاء مهلة، إلغاء عميل، تعذر تسليم، استلام من الفرع.
2. سكربت نسخ احتياطي واستعادة، مع اختبار يستعيد إلى قاعدة فارغة ويقارن عدد الصفوف.
3. `docs/RUNBOOK.md`: التشغيل المحلي، المتغيرات، النشر، إنشاء أول مدير، النسخ والاستعادة.
4. `docs/API.md` مولَّد من `contracts`.
5. مراجعة أمنية ذاتية مقابل SPEC §16 وتدوين النتائج في `docs/SECURITY_REVIEW.md`.
6. تحديث `docs/OPEN_QUESTIONS.md` بكل ما بقي معلقاً.

**القبول**
- كل أوامر القسم (ب) خضراء من نسخة نظيفة.
- لا `TODO`/`FIXME` بلا مرجع في `OPEN_QUESTIONS.md`. لا `any` صريح. لا `@ts-ignore`.
- لا اختبار متخطّى (`skip`) بلا سبب مكتوب.

## د. بوابات تحقق خارجية (لا تحسمها أنت)

هذه تحتاج اختباراً بشرياً من داخل سوريا. ابنِ خلف الواجهات المجردة، ولا تُدخل SDK لمزوّد حقيقي ولا تكتب في أي مستند أن خدمة ما «تعمل في سوريا».

| البوابة | السؤال | أثرها على الكود |
|---|---|---|
| SMS | أي مزوّد يوصل OTP لأرقام Syriatel و MTN بموثوقية وبكلفة مقبولة؟ هل واتساب بديل؟ | تنفيذ جديد لـ `OtpProvider` فقط |
| Push | هل FCM و Google Play Services متاحة وموثوقة على أجهزة المستخدمين؟ | تنفيذ `PushProvider`. النظام يعمل بدونه بالسحب |
| تنبيه المطعم والتطبيق مغلق | إن لم يكن Push موثوقاً: هل نحتاج خدمة أمامية (foreground service) تسحب في الخلفية؟ | إضافة لتطبيق المطعم فقط |
| الاستضافة | هل الخادم و CDN الصور قابلان للوصول من شبكات سورية دون VPN؟ | متغيرات بيئة فقط |
| التوزيع | Google Play أم APK مباشر أم الاثنان؟ وآلية التحديث؟ | إعداد البناء |
| القانوني | تسجيل النشاط، شروط الاستخدام، سياسة الخصوصية والاحتفاظ بالبيانات | نصوص وصفحات ثابتة |
